# 第一阶段优化原理与面试问答

## 1. 这次优化解决了什么

原实现的 `yolov5_detect()` 每处理一帧都会读取 5,208,887 字节模型，调用
`rknn_init()`，查询输入输出信息，并在结束时调用 `rknn_destroy()`。这些操作
属于推理引擎生命周期管理，不属于逐帧计算。

优化后生命周期为：

```text
线程启动：读取模型 → rknn_init → 查询张量
每一帧：预处理 → rknn_inputs_set → rknn_run → outputs_get → 后处理
线程退出：rknn_destroy
```

板端实测单次初始化为 47.8～82.9 ms。旧实现把这部分成本和 5.2 MB 磁盘读取
放进了每一帧；新实现只在启动阶段支付一次。

## 2. 为什么必须分阶段测量

只在 `rknn_run()` 前后计时会漏掉大量真实成本。当前 100 次 Release 基准为：

| 阶段 | 平均值 | P50 | P95 |
|---|---:|---:|---:|
| letterbox/BGR→RGB | 1.294 ms | 1.095 ms | 2.088 ms |
| `rknn_inputs_set` | 56.867 ms | 50.980 ms | 94.074 ms |
| `rknn_run` | 109.006 ms | 108.663 ms | 120.855 ms |
| `rknn_outputs_get` | 26.884 ms | 18.996 ms | 50.663 ms |
| CPU 后处理 | 3.001 ms | 2.647 ms | 4.187 ms |
| YOLO 总耗时 | 197.065 ms | 193.231 ms | 240.961 ms |

测试先预热 5 次，随后记录 100 次。当前硬件传感器未就绪，所以这些数据只代表
RKNN 子链路，不代表完整融合帧率。

平均值只能说明吞吐趋势，P95/P99 才能说明实时系统中的尾延迟。实时视频中偶发
的 200 ms 卡顿会造成队列积压，即使平均值看起来不差。

计时使用 `CLOCK_MONOTONIC`，因为系统时间被 NTP 或人工调整时，单调时钟不会
回退。统计输出每 5 秒聚合一次，避免逐帧 `printf` 反过来污染性能。

## 3. 如何读懂 RKNN 张量

板端实际查询结果：

```text
input : 1×640×640×3, FP16, NHWC, 2,457,600 bytes
output: 1×25200×85, FP16, 4,284,000 bytes
```

- `NHWC` 表示批次、高、宽、通道的内存顺序。
- 输入大小为 `640×640×3×2`，最后的 2 是 FP16 每元素 2 字节。
- `25200 = 80×80×3 + 40×40×3 + 20×20×3`，对应三个检测尺度和每尺度
  三个 anchor。
- `85 = 4 个框参数 + 1 个目标置信度 + 80 个类别概率`。

应用现在给 `rknn_inputs_set()` 传 UINT8，而模型原生输入是 FP16，因此 Runtime
需要复制并转换约 1.23 MB 输入，这很可能是 `rknn_inputs_set` 平均 52.5 ms 的
主要来源。`outputs_get(want_float=1)` 还会把 FP16 输出转换为 FP32，造成额外
分配、复制和转换。需要用 A/B 实验进一步拆分贡献，不能只凭现象断言百分比。

下一阶段最有价值的两个方向是：

1. 使用 RKNN Toolkit2 生成经过代表性数据集校准的 INT8 模型。
2. 通过 `rknn_set_io_mem()` 绑定预分配输入输出，减少 Runtime 内部复制。

## 4. 为什么使用 letterbox

原图是 640×360，模型输入是 640×640。直接 `resize(640, 640)` 会改变目标宽高比，
圆会变成椭圆，检测框也更容易偏移。

letterbox 保持比例缩放，再在空白区域填充 114。本项目中横向比例为 1，图像
仍为 640×360，上下各填充约 140 像素。后处理需要执行逆变换：

```text
原图坐标 = (模型坐标 - padding) / scale
```

如果只做前处理而忘记框坐标逆映射，显示出来的框会产生固定偏移。

## 5. V4L2 基线中为什么要检查协商结果

`VIDIOC_S_FMT` 中填写的是请求值，不是驱动必须接受的值。调用成功后，驱动可以
返回最接近的分辨率、stride 和缓冲区大小。因此必须读取返回的：

- `width`、`height`、`pixelformat`
- `bytesperline`
- `sizeimage`

后续 DMA-BUF/RGA 优化尤其不能假定 `stride == width`。忽略 stride 可能表现为
花屏、图像错行或越界访问。

## 6. 当前拷贝链路

一帧 640×360 NV12 为 345,600 字节。当前至少存在四次显式整帧复制：

1. V4L2 MMAP Buffer → 实时共享 Buffer。
2. V4L2 MMAP Buffer → 15 帧同步队列。
3. 共享 Buffer/同步队列 → OpenCV 线程局部 Buffer。
4. 局部 Buffer → OpenCV NV12 Mat。

合计约 1.38 MB/处理帧；30 FPS 时约 41.5 MB/s。这还没有计算 OpenCV 和 JPEG
内部的复制。第一阶段先测清楚，下一阶段再改变 Buffer 所有权模型。

## 7. 高频面试问题与回答思路

### Q1：为什么 `rknn_init()` 不能每帧调用？

它需要解析模型、建立 Runtime/NPU 资源并准备内部内存。模型和张量结构在视频
流中不变，因此应按进程或推理实例初始化一次。逐帧初始化会增加延迟、内存抖动
和失败概率。

### Q2：为什么不能只报告 NPU 推理时间？

用户感知的是端到端延迟。输入格式转换、Runtime 输入复制、输出反量化和 NMS
都可能比预期更贵。本项目中 `inputs_set + outputs_get` 平均约 77 ms，不能忽略。

### Q3：P50、P95、P99 分别表示什么？

P50 是中位数；P95 表示 95% 样本不超过该值；P99 更关注极端尾延迟。实时系统
应同时关注吞吐和尾延迟，因为长尾会引起积压、丢帧和画面卡顿。

### Q4：为什么需要预热？

首次运行可能触发模型内部初始化、内存映射、缓存缺失和 DVFS 升频。将预热样本
混入统计会让稳定态结果不可复现。

### Q5：`rknn_inputs_set()` 为什么这么慢？

当前应用传 UINT8 NHWC，而模型原生张量是 FP16 NHWC。Runtime 需要申请或复用
内部空间并完成 UINT8→FP16 转换和复制。下一步可用 INT8 模型、预分配 I/O Memory
和 RGA/DMA-BUF 做 A/B 验证。

### Q6：`rknn_run()` 返回后推理一定全部结束了吗？

不能只凭函数名推断异步语义，应结合 Runtime 模式和官方 API 行为验证。因此本
项目分别测量 `rknn_run()` 与 `rknn_outputs_get()`；后者可能包含等待和输出转换。

### Q7：为什么 FP16 输出还设置 `want_float=1`？

旧后处理代码使用 `float*`，所以 Runtime 将输出转换为 FP32，开发简单但代价较大。
优化时可以直接读取 FP16/量化输出并在 CPU 上解码，或使用预分配输出内存，但要
同步修改量化公式和后处理。

### Q8：letterbox 和直接 resize 的区别是什么？

直接 resize 简单但破坏宽高比；letterbox 保持几何形状，却要求后处理减去 padding
并除以 scale。检测项目通常优先保证几何一致性。

### Q9：常驻 Context 是否线程安全？

当前 Context 只由 OpenCV 推理线程使用，不存在同一 Context 并发调用。若以后增加
多推理线程，应使用独立 Context 或按照 RKNN Runtime 的线程安全约束加同步，不能
直接共享后假定安全。

### Q10：为什么第一阶段还不叫零拷贝？

因为 `rknn_inputs_set()` 仍复制/转换输入，V4L2 图像也仍复制到用户态队列。第一
阶段解决生命周期和可观测性；只有建立 DMA-BUF fd 共享、明确 Buffer 所有权和同步
关系后，才可以称“推理关键路径零拷贝”。

### Q11：MMAP 和 DMA-BUF 是互斥的吗？

不是。摄像头可先用 `V4L2_MEMORY_MMAP` 申请驱动 Buffer，再用 `VIDIOC_EXPBUF`
导出 DMA-BUF fd 供 RGA 使用。`V4L2_MEMORY_DMABUF` 则表示应用把外部分配的
DMA-BUF 导入驱动，语义不同，并且要求驱动支持该模式。

### Q12：如何证明优化没有破坏检测结果？

固定输入集、模型和阈值，对比优化前后的检测框数量、类别、置信度与 IoU；性能
测试之外还要做正确性回归。INT8 量化时还应在验证集上比较 mAP，不能只看速度。

## 8. 面试讲解顺序

建议按“问题—证据—改造—结果—下一步”讲：

1. 原系统能完成双光融合，但 YOLO 开启后延迟明显。
2. 分段埋点发现初始化、输入转换和 NPU 推理不能混为一个指标。
3. 将 RKNN 生命周期常驻化，加入 letterbox、张量检查和分位延迟统计。
4. 100 次基准证明单次初始化成本被移出逐帧路径，并暴露 FP16 输入转换瓶颈。
5. 下一阶段用 INT8、RGA、DMA-BUF 和 RKNN I/O Memory 消除转换与复制。

不要背结论。面试官追问时，从数据流、内存所有权、张量格式和时间测量四条主线
推导即可。
